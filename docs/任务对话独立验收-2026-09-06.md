## 发现与处理状态

### F1 / P1：首轮完成后仍发送旧任务版本，连续追问失败

定位：`web/src/Path2Workbench.tsx:2768`，`web/src/TaskDialogue.tsx:61`、`:103`、`:197`。

复现：

1. 进入已有合成任务，明确勾选资料，发送带关系引用的问题。
2. 等到用户消息、Agent 答复与执行历史都可读取。
3. 不 reload 页面，发送第二个问题。
4. 页面提示“任务状态或历史内容已变化”；点击“刷新对话”后再发送仍提示同一冲突。

实测首次请求使用 state version 6；运行期间前端读到 version 7，运行结束后服务端 Mission 已为 version 8、status blocked。第二次发送仍携带 version 7。点击“刷新对话”后下一次请求仍为 7，两次都被后端拒绝。

代码证据：SSE 后续读回调用 `refreshRunSnapshot`，不刷新 Mission；composer 的 refresh 只读取消息与执行列表，下一轮请求从旧 `missionSnapshot` 提取版本。后端版本检查正确拒绝请求，前端恢复动作不完整。

影响：用户最核心的连续追问流程被阻断。整页 reload 能恢复新版本，但会清空未提交草稿和资料选择，不能算该流程验收通过。

最小修复建议：在本轮结束及状态冲突核对时统一读回 Mission、当前 Run 和消息；按任务与 Run 身份防止过期响应覆盖。保留用户草稿，不自动重发，也不能通过放宽后端版本检查掩盖问题。

状态：`ACCEPTED / PENDING_FIX`。证据截图：`07-followup-conflict.png`。

### F2 / P2：答复已保存，右侧仍显示“答复未保存”

定位：`web/src/Path2Workbench.tsx:2722`，`web/src/TaskDialogue.tsx:189`。

实测在 F1 的首轮执行后，对话中已经出现新 Agent 答复，中间执行列表和详情均可读取“已保存公开答复”，但右侧底部持续显示“答复未保存；可查看本轮结构化结果”，且任务仍显示 active。页面等待及切换执行历史后仍不一致，整页 reload 后恢复。

代码证据：Run 状态一旦为 terminal，effect 转为仅回放历史事件的路径；该路径不补读最新 Run。后端保存公开答复与终态事件存在先后步骤，因此读到终态但缺少最终公开输出的窗口需要被处理。确切触发时序仍需修复时用可控测试固定；本次 UI 矛盾和持久读回已直接证实。

影响：页面对保存结果作出错误判断，会让用户误以为答复丢失。它与 F1 都涉及读回，但不能只改状态文案就算修好。

最小修复建议：完成本轮持久结果核对后再判定保存状态；区分“正在核对”与“未保存”，确保当前 Run、Mission 和消息来源一致。用延迟保存 final output 的用例验证。

状态：`ACCEPTED / PENDING_FIX`。证据截图：`07-followup-conflict.png`，中间的持久答复与右侧提示同时可见。

### F3 / P2：引用与默认历史缺少资料范围的发送前提示

定位：`web/src/TaskDialogue.tsx:85`、`:173`。

实测重新进入已有任务后，默认选择最近两条历史，但已选资料为 0。进入关系结果并点击“引用关系继续讨论”，写问题后“发送并分析”可点击。提交包含 2 条历史、1 个关系引用、0 份资料，后端返回 409：所选历史或草案包含本轮未选资料。

最小修复建议：发送前明确显示缺少的引用资料及补选入口；由用户显式确认范围。不要因为浏览或引用就自动扩大模型发送权限。历史建议也应明确显示当前范围不满足，而非到提交后才报错。
