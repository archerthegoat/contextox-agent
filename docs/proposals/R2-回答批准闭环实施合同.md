## 1. 已批准行为和本次范围

用户已定：整份回答一起批准；允许批准“尚不能确认”的记录并继续，但问题未解决，每个卡点有解决方、所需证据、下一动作；补充事实更新原澄清请求的整份新版本、重新批准；旧 Run 保留旧回答快照。批准未知不等于批准结论，批准回答不等于批准最终草案或 Mission 完成。

本次设计从已产生的澄清请求开始，交付“录入 → 保存整份回答 → 审阅批准 → 显式继续 → 看到草案变化与剩余卡点”。不新增角色系统、通知/外发、真实业务身份认证、正式 Contract、跨任务知识复用、Provider、依赖或预算。保存、批准、查看、刷新均不调用模型；只有显式“继续分析”可按既有授权范围和预算发起新 Run。

事实基线：`ClarificationRequest.status` 只有 `awaiting_answer`；原问题没有问题 ID；Store 保留不可变请求并由任何历史请求阻塞后续消息；ContextSnapshot 对旧请求强制同 Run 身份；候选只支持技术来源 EvidenceRef，没有人工回答证据类型。本设计分别补回答版本、有效批准与 Run 绑定，不修改历史请求来伪装兼容。

## 2. 对象与精确数据语义

沿用 ID、Hash、UTC、严格整数、EvidenceRef、SourceIdentity；所有 Pydantic 对象 `extra=forbid`。所有父子查验包括 workspace_id、mission_id、origin_run_id、clarification_id，不按全局裸 ID 寻址。

### 2.1 问题身份

`ClarificationRef={origin_run_id:ID, clarification_id:ID}`。

`question_index` 是原请求 questions 的零基索引，0..19。原问题文本、顺序、草案版本/hash 保持不可变；原请求快照的 `request_sha256=canonical_sha256(原 ClarificationRequest 完整 JSON)`。回答新版本不能改题、删题或换请求。新增问题继续通过已有领域工具形成新请求，不能将上一请求改成另一组问题。

`DefinitionTarget` 为以下判别联合：

- `{kind:"field", key:Key, property:"meaning"|"value_type"|"grain"|"rule"|"time_basis"|"null_handling"}`；
- `{kind:"relationship", key:Key, property:"join_rule"|"grain_notes"}`；
- 不把任务级自由文本 unresolved_items 强塞进 Key。任务级/尚无对象的问题由 `{origin_run_id,clarification_id,question_index}` 作为持久卡点身份，无须已有草案字段。

问题原 `related_definition_paths` 属于不受结构约束的字符串，不能猜测成可靠对象。回答页始终展示原路径；用户可选实际影响维度，选项从当前审阅草案生成。每题 targets 0..20，不重复，已选择的目标保存时验证存在。原路径不能解析时保留原文并显示“尚未绑定具体定义维度”，不阻止回答；缺失资料、尚未创建字段、空草案等问题都可仅按问题身份回答。选择的影响对象与回答一起被批准；未选择不代表问题不存在。已选择 target 在当前草案已删除时，仍携带旧 target 的保存/批准/继续返回 `clarification_target_stale`，保留记录；人可在原请求的整份新版本里重新选择 target 或移除失效映射后重批，问题身份及原回答历史保留。首版不自动迁移到同名对象。

### 2.2 整份回答版本

```text
AnswerItem={
 question_index:0..19, disposition:"answered"|"unknown",
 answer:string|null, respondent:string(1..128), basis:string(1..2048),
 evidence_refs:list[EvidenceRef](<=8), targets:list[DefinitionTarget](<=20),
 blocker:{resolver:string(1..128), evidence_needed:string(1..2048), next_action:string(1..2048)}|null
}
ClarificationAnswerVersion={
 workspace_id, mission_id, origin_run_id, clarification_id,
 version:PositiveInt, request_sha256:Hash,
 review_draft:{draft_id:ID,version:PositiveInt,sha256:Hash},
 source_refs:list[SourceIdentity](<=8), items:list[AnswerItem](1..20),
 saved_by:"local-owner", created_at:UTC, sha256:Hash
}
```

整份 items 精确覆盖原请求所有索引各一次，按索引升序；answered 时 answer 必须为 1..2048 字符非空白文本，blocker=null；unknown 时 answer=null，blocker 三项必填。respondent/basis 是人的来源声明，不是系统验证过的职位权限或企业批准。unknown 的 basis 解释目前不能确认的原因。用户可写角色或具体人作为 resolver；找不到最终专家时填写承担寻找专家责任的解决方及明确动作，不能留空占位并声称已分派。系统不发消息，不保证对方已接受任务。

source_refs 从当前任务授权来源确定并完整绑定版本；EvidenceRef 必须属于它们并可读取。无文档证据的业务裁决可用 respondent+basis，不能伪造 EvidenceRef。字符串不自动 trim 改写原文；验证非空白。整份版本 canonical UTF-8 JSON <= 131072 字节，超限整份拒绝，不能截断。

sha256 绑定上述全部字段，排除 created_at 与 sha256；包含版本、身份、request hash、当前审阅草案、来源、每题回答/卡点/影响目标。版本不可变，任何修改都创建 N+1，必须重批；旧批准仍可审计但不再供新 Run 选择。草稿未完整时留在当前页面，不向后端提交不完整版本；刷新前提示未保存。

### 2.3 整份批准

```text
ClarificationAnswerApproval={
 workspace_id, mission_id, origin_run_id, clarification_id,
 answer_version:PositiveInt, answer_sha256:Hash,
 approval_id:ID, approved_by:"local-owner", approved_at:UTC
}
ApprovedAnswerRef={origin_run_id,clarification_id,answer_version,answer_sha256,approval_id}
```

一版本最多一个批准，重复批准同版本读回原记录。批准针对完整列表及来源/影响范围；不能逐题批准。批准时要求该版本仍为最新、来源可读且版本有效、review_draft 等于当前草案；同时检查原问题绑定草案仍可回读。批准未知只确认此未知及处理安排，不把问题标为 resolved。

当前展示用 `ClarificationCase` 包含 immutable request、request_sha256、latest_answer|null、latest_approval|null，以及派生 `review_state=awaiting_answer|awaiting_approval|approved|stale`。不复用或改写原 ClarificationRequest.status。问题派生 `knowledge_state=answered|unresolved` 与 review_state 分离；unknown 始终 unresolved，无论是否 approved。

## 3. API 与事务

以下路径前缀统一为 `/api/workspaces/{workspace_id}/missions/{mission_id}`；`{ref}` 展开为 `/clarifications/{origin_run_id}/{clarification_id}`，防止同名和历史请求混淆。

| 方法与路径 | 请求/结果 |
| --- | --- |
| GET `/clarification-cases` | items: ClarificationCase[]；最多 50 个请求，超过时 `clarification_scope_too_large` 明确阻塞，不截断待决项 |
| GET `{ref}/answers/{version}` | 精确版本与其批准或 null；历史只读 |
| POST `{ref}/answers` | client_request_id、expected_latest_version:Count(首版0)、expected_state_version、request_sha256、review_draft、source_refs、items；201 新版本/200 幂等读回 |
| POST `{ref}/answers/{version}/approve` | client_request_id、expected_state_version、expected_answer_sha256；201 新批准/200 幂等读回 |
| GET `/clarification-submissions/{client_request_id}` | 已接受的保存或批准回执，含 operation、原对象身份和当前可读结果；404 无记录 |

保存/批准成功回执统一返回 `{operation,client_request_id,answer:ClarificationAnswerVersion,approval:ClarificationAnswerApproval|null,mission_state_version:PositiveInt}`，包含事务提交后的版本供下一动作 CAS；重放时 answer/approval 身份不变，mission_state_version 返回当前可读值。列表返回 `{items:list[ClarificationCase],mission_state_version:PositiveInt}`。

所有 mutation 使用同一任务内独立的 clarification submission ID 域；和模型发送 ID 分开，operation 参与请求 hash。每次完整请求 canonical hash 包括 CAS 字段；同 ID 同 hash 读回、不同 hash 409 `idempotency_conflict`。在当前授权校验后先查询旧提交，再做新动作 CAS，避免重放被旧 expected_state 拒绝。网络结果未知时仅查回执或同 ID 同负载重提，不产生新 ID 自动再做。

写事务原子完成：父对象/权限/无活动 Run 校验 → 当前 Mission state_version CAS → 最新回答版本 CAS → hash/范围/新鲜度校验 → 插入不可变版本或批准、submission → Mission state_version +1 → commit。新版本产生后，旧批准自动不符合“最新版本”条件，不删除或撤销历史。失败全回滚，保存/批准均不改变 Mission 为 active，不改 DefinitionDraft。

补充现有 `TaskMessageSendRequest` 字段 `approved_answers:list[ApprovedAnswerRef]` 默认 []，最多 50、按 origin_run_id/clarification_id 排序且不重复，以及 `expected_draft:{draft_id:ID,version:PositiveInt,sha256:Hash}|null` 默认 null。approved_answers 非空时 expected_draft 必填；两者均为空时保持原请求 hash 算法，两者一起参与非空 R2 请求 hash。新 Run 入库时把精确绑定与 Run、消息置于同一事务。旧 run/start 入口仍不允许绕过等待澄清。

继续必须满足：所有历史请求均保留作为当前任务应核对的问题集合（不因原 Run 已结束而消失），均有最新版本批准，选择集恰好是当前全部批准；sources 与批准版本集合精确一致且可读；所有目标在当前草案仍存在；无 in_review 草案；无活动 Run；既有 Provider 结果对账通过。允许 waiting_for_human → active，但保留旧 Run 原终态。未批准、最新版本改变、少选一份、任一 hash 不一致均 409，不能回退消费旧批准。普通发送默认 [] 在存在请求时明确提示先完成批准；UI 显式“继续分析”装配已展示的集合并沿用 provider_send_confirmed。

业务回答的有效性与候选草案 CAS 分开：review_draft 用于保存→批准期间确保人审阅的是同一草案，批准时发现草案变化则返回 stale，用户核对后保存整份新版本再批。批准成功后，Agent 产生新候选草案不会自动撤销业务回答。后续继续以 expected_state_version 及新增 expected_draft={draft_id,version,sha256} 对当前草案单独 CAS，并将它作为本 Run 的 before_draft；有效批准仍由原问题/hash、最新回答版本/hash、来源版本/授权及可选 target 存在性决定。无关字段增补不触发整份重批，也不设时间到期。删除已选择目标、来源变化或人修改原回答才使受影响批准不可继续使用。候选值与已批回答有差异时展示冲突，不能把模型新候选当作更高权威来覆盖人工声明；人若改变业务结论，应更新原回答整份版本重批。

## 4. Run 上下文、候选与差异

`RunSnapshot.approved_answers` 和 `ContextSnapshot.approved_answers` 新增只读列表，默认 []。它们使用独立模型表达来源 Run，与当前 clarifications 的同 Run 校验分开。只装配该 Run 入库时绑定的不可变版本，永远不查询“最新回答”替换历史。

`ContextManifestInput.approved_answer_refs` 默认 []；非空时参与 manifest hash，ProviderReceipt 继续绑定 manifest hash。旧空列表从 canonical hash 输入排除，保持所有历史 hash 可验证。Context manifest 每轮都保持同一组 Run 绑定；拒绝模型/客户端自行变更。上下文传给模型只包括问题、回答、依据、影响目标、未解决卡点和精确引用，不重复全部审批回执、历史版本或聊天。新输入和已有来源、工具仍共用原 max_context_bytes；整份超限在发模型前拒绝 `approved_answer_context_too_large`，不得截断问题。

Agent 明确把批准的 answered 看作任务内人工声明，不能将其伪装为资料观察。现有字段/关系仍标 candidate，source_refs 继续表示技术证据；UI 单列“本轮采用的回答”与“资料证据”。本期不新增人类回答 EvidenceRef 类型或正式逐字段批准。字段变化与回答的关联由 targets 和本轮固定批准列表确定，展示“相关已批回答”，不能声称模型每一句都已被人批准。

unknown 的保护在 Store 候选写入边界实施：映射到字段维度时该维度仍 null 且 unknowns 保留；映射关系 join_rule/grain_notes 同理。未绑定 target 的 unknown 由批准输入中的问题卡点持续保存和展示，不依赖模型的 unresolved_items 文本才能存在。即使模型填写猜测也拒绝该写入，给已有有界恢复机制明确错误 `approved_unknown_must_remain_unresolved`。answered 与 unknown 对同一已绑定 target 冲突时 unknown 优先且显示冲突，必须更新整份回答重批才能解除；不能取最后一项。

上述程序保护仅覆盖显式绑定维度；未绑定问题不能据此宣称系统能阻止任意新字段中的同义猜测。模型需保留这些问题的不确定性，是否无依据造出新语义仍是 G3 真实语义验收项。无论模型输出如何，问题级 unknown 卡点不会被自动解决。

新 Run 可以继续读取资料、分析其他对象、提交候选或形成新澄清。已批准回答不是只允许修改 targets 的白名单：新探索可能合理补充其他对象，但差异页必须分成“与本次回答相关”及“其他分析变化”，避免误称全部因批准造成。相同请求 unknown 后来得到事实，更新原请求回答，而非新建重复问题消除旧卡点。

差异读接口：GET `/runs/{run_id}/answer-impact`，返回 `approved_answers`、`before_draft`、`after_draft|null`、按 field_key/relationship_key 对齐的 added/changed/removed（每项前后完整值与匹配的 question refs）、remaining_blockers、`result_state=no_result|partial|available`。before 为继续入库时的精确草案，after 为该 Run 自身最新持久版本，不能使用任务后来最新草案。没有新版本就是 no_result，失败前已写出部分版本就是 partial，不伪造空差异为成功。关系/字段 hash 沿用原算法，不因旁侧回答来源显示而改写历史草案。

## 5. v5 迁移提案

采用现有 SQLite 明确 schema 校验、离线备份及事务迁移模式，由 v4 → v5。v3 先沿既有获批 v4 路径，不跳过验证。以下是新增表字段的精确逻辑设计，DDL 展开时不得改变键/约束语义：

| 表 | 列与键 |
| --- | --- |
| clarification_answer_versions | workspace_id, mission_id, origin_run_id, clarification_id, version INTEGER CHECK>0, sha256, payload_json；PK 前四身份+version；UNIQUE 同键+sha256；前四身份 FK 原 clarification_requests(workspace_id,mission_id,run_id,clarification_id) |
| clarification_answer_approvals | workspace_id, mission_id, origin_run_id, clarification_id, answer_version, answer_sha256, approval_id, approved_by CHECK='local-owner', approved_at；PK 前四身份+answer_version；UNIQUE(workspace_id,mission_id,approval_id)；FK 前四+版本/hash 到 versions |
| clarification_submissions | workspace_id, mission_id, client_request_id, operation CHECK IN('save','approve'), request_sha256, origin_run_id, clarification_id, answer_version；PK workspace/mission/client_request_id；FK 前四请求身份+answer_version 到 versions |
| run_approved_answers | workspace_id, mission_id, run_id, origin_run_id, clarification_id, answer_version, answer_sha256, approval_id；PK workspace/mission/run/origin_run/clarification；FK 当前 Run；FK 原问题+版本/hash 到 versions；FK workspace/mission/approval_id 到 approvals |

`context_manifests` 新列 `approved_answer_refs_json TEXT NOT NULL DEFAULT '[]'`。所有 JSON 字段必须严格 Pydantic 验证及 canonical 比较；approval 与 run 绑定的跨 FK 版本一致性在事务和读取时双重校验，不只验证 approval_id 存在。Run 开始时 before_draft 复用该 Run 首个 manifest 的草案；为避免 worker 尚未开始时无 manifest，继续发送事务必须先保存合法 turn_index=1 manifest，Agent 首轮只校验并复用，不重复插入。该调整仅用于 R2 非空绑定，新旧普通 Run 不变。

不修改历史 request.status、不补造回答、不改 Run/events/ProviderReceipt 记录。旧库迁移后历史页面显示尚无回答；旧未知 Provider 结果不会因迁移被核销。备份包括 SQLite 及既有私有 sources 文件清单/hash；备份留在运行数据目录，不进 Git。

迁移要求服务停止、无活动 worker；持有写锁；迁移前 exact v4 schema/integrity/FK 校验；生成可核对备份；单事务新增表/列、user_version=5、exact schema 校验后提交。失败回滚，原库保持 v4；无自动覆盖恢复。旧二进制必须拒绝 v5 库。回退先停止服务，保留 v5 完整库与迁移后的所有写入，再使用单独 v4 备份路径启动旧版本；不删除新回答来降级。无线上迁移、无新依赖。

## 6. 页面流程与失败

复用当前任务问题卡与草案页。原对话中已认可的澄清原型不在当前工作树，不能假定其 URL 仍能运行；实现前仅核对/补齐此流程所需交互，不重新设计工作台。当前合同文档不是可试用原型，也不是 UI 验收。

1. 问题列表显示原问题/影响/证据与每题 answered/unknown 控件，可选关联实际影响维度；保存整份回答前显示遗漏。
2. 保存成功显示整份版本与回答来源，按钮“批准整份回答”；unknown 行突出解决方、所需证据、下一动作。
3. 批准后单独提供“继续分析”，旁边明确本次携带几份回答、多少未解决卡点和现有请求上限。批准本身不会偷偷运行。
4. 分析期间只读；完成/失败都可打开该 Run 的精确回答及草案变化。历史页面不得出现当前版本编辑按钮。
5. 修改回答显示“整份新版本需要重新批准”，不能沿用旧绿色批准标记。

| 反例/故障 | 必须行为 |
| --- | --- |
| 双击保存/批准、服务提交后响应丢失 | 同 ID 查回原版本/批准；不重复 state_version+1 |
| 两个页面同时修改/批准 | 后提交 CAS 409，保留本地输入，用户回读比较 |
