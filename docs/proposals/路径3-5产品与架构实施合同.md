# 路径 3–5 产品与架构实施合同

状态：`PROPOSED — 等待受控文档精确批准`

日期：`2026-09-12`
目的：把现有 Demo 1.0.0 的候选定义闭环推进到正式定义交付、批准知识复用和可比较的价值验证，同时完成分享会品牌展示包。

本合同不自动修改 `开发路径图.md` 或 `docs/架构与迁移报告.md`。只有 `docs/proposals/2026-09-12-产品架构受控文档待批准.diff` 的精确差异获人批准后，受影响的产品代码、迁移和受控文档才可实施。品牌展示包不改变产品状态，已经作为独立可回滚切片实现。

## 1. 当前基线与缺口

当前源码已经具备 Workspace 隔离、受限来源、确定性 Profile、连续对话、候选字段/关系/未知项、澄清回答候选、整份精确批准、确认续接、版本变化和候选导出。现有结果仍为 `DefinitionDraft`，`semantic_approval` 保持 pending；`submit_for_review` 只冻结候选，`finish_run` 不能把当前 Demo 结果直接提升为 Mission 完成。

下一阶段必须补齐的不是新的通用 Agent 框架，而是三段产品合同：

1. 候选定义如何经过正式审阅成为不可变 `ContractVersion`；
2. `ContractVersion` 如何生成经批准的 `WorkspaceContextVersion`，并在第二个 Mission 中由系统建议、由用户显式选用；
3. 同一材料、目标和预算下，如何把 ContextOx 与通用 Agent 的结果和人工投入作可复核比较。

## 2. Pi Agent 参考结论

参考成熟 Agent Runtime 的价值在于明确生命周期和上下文变换边界，而不是迁移框架。ContextOx 继续使用自有薄 Python Loop，只借鉴以下模式：

- 在每次 Provider 请求前由程序从权威状态编译有界上下文，而不是累积不可控 transcript；
- 运行事件、持久业务对象和展示状态分层；
- 追加式会话历史可回读，派生 summary 可以重建；
- 用户追问只在当前调用结束后的安全消息边界进入下一轮，不热注入正在执行的工具或事务。

不采用通用 `read/write/edit/bash`、Coding Agent 会话语义、Agent subdelegation、框架内存、自动工具重试或以 `agent_end` 代表业务完成。Workspace、权限、证据、批准、Contract 与 Mission 完成仍由 ContextOx 领域层决定。

## 3. 目标状态机

```text
DefinitionDraft
  draft ──submit──> in_review
  in_review ──request_changes──> draft
  in_review ──approve_exact_version──> approved
  approved ──publish──> ContractVersion.published

ContractVersion.published
  ──compile_context_candidate──> WorkspaceContextCandidate
  ──approve_exact_version──> WorkspaceContextVersion.approved
  ──supersede | revoke──> stale | revoked

New Mission
  ──deterministic_match──> ContextReuseSuggestion
  ──user_selects_exact_versions──> ContextReuseDecision.accepted
  ──ContextPacketManifest──> Provider request
```

任何阶段的模型输出、自然停止、Run completed、候选导出或澄清回答批准，都不能跳过正式 Contract 审阅、Context 批准或 Mission 完成校验。

## 4. 冻结领域对象

### 4.1 `ContractVersionV1`

必需字段：

```text
workspace_id
mission_id
contract_id
version
status: in_review | published | superseded | revoked
business_purpose
entities[]
grain[]
identity_rules[]
time_semantics[]
source_mappings[]
field_definitions[]
metric_definitions[]
calculation_rules[]
exceptions[]
known_unknowns[]
positive_examples[]
negative_examples[]
owners[]
acceptance_criteria[]
source_revision_refs[]
approved_answer_refs[]
draft_version
draft_hash
content_hash
created_at
published_at
supersedes_version
```

`status=published` 只允许由本地使用者批准精确 `draft_version + draft_hash + content_hash` 后的事务产生。必需维度缺失、引用陈旧、来源权限未知、回答版本不匹配或仍有阻塞未知时拒绝发布；非阻塞未知必须显式保留在 `known_unknowns`。

### 4.2 `ContractReviewDecisionV1`

```text
workspace_id
mission_id
contract_id
candidate_version
candidate_hash
decision: approve | request_changes | reject
decided_by: local-owner
reason
created_at
client_request_id
```

相同 `client_request_id` 和相同 payload 幂等回读；不同 payload 冲突。审批不能由模型工具、职位名称或导入文件代替。

### 4.3 `MissionCompletionReceiptV1`

```text
workspace_id
mission_id
contract_id
contract_version
contract_hash
required_acceptance_checks[]
evidence_refs[]
terminal_run_id
terminal_receipt_id
completed_at
```

只有发布后的 Contract、任务模板要求的验收项、所需证据和显式终止收据全部匹配时，Mission 才能从 active/waiting_for_human 转为 completed。

### 4.4 `WorkspaceContextVersionV1`

```text
workspace_id
context_id
version
status: candidate | approved | stale | revoked | conflict
subject_type: entity | field | metric | rule | mapping | exception
subject_key
statement
scope
valid_from
valid_until
contract_ref
source_revision_refs[]
approval_ref
content_hash
supersedes_version
```

只有 `approved` 且未过期、未撤销、无冲突、权限匹配的版本可进入复用候选。`MEMORY.md` 只是该对象的可重建投影，不能成为权威来源。

### 4.5 `ContextReuseSuggestionV1` 与 `ContextReuseDecisionV1`

Suggestion 由确定性匹配产生，包含新 Mission、候选 Context 精确版本、匹配理由、作用范围、冲突/时效状态和来源摘要；它不进入 Provider 请求。用户在对话或 Workbench 操作组件中逐项选择、跳过或查看依据后，产生绑定精确版本的 Decision。只有 accepted Decision 可进入本轮 `ContextPacketManifest`；默认不自动选中，不因历史上曾批准而静默复用。

## 5. Workbench 交互

### 5.1 正式定义交付

- 对话仍是入口；中间工作区新增“候选定义 / 审阅差异 / 正式版本”三个业务视图，不增加新的顶层产品导航。
- 候选满足提交条件时，右栏只出现一个主要动作“提交审阅”；审阅态主要动作是“批准并发布”，次要动作是“要求修改”和“查看技术详情”。
- 审阅页默认显示业务名称、定义正文、来源、未知、例外和验收条件；版本、hash、对象键和收据按需展开。
- 发布前展示精确版本与变化摘要；发布后返回不可变回执、可导出 JSON/Markdown 和 Mission 完成状态。导出不等于发布。

### 5.2 批准知识复用

- 新 Mission 建立后，若存在匹配的批准 Context，右栏显示“找到 N 条可能相关的已批准定义”。
- 用户可查看来源与适用范围，逐项选择“用于本任务”或“这次不用”。默认全部未选。
- stale、revoked、conflict、权限不匹配和版本未知项只显示风险，不可选用。
- 被选项写入本轮 Manifest，并在答复和正式成果中可定位；没有选用的项不发送给 Provider。

## 6. 实施切片与门

### C0 — 合同冻结

- 精确批准本合同对应的受控文档 diff。
- 为 v7→v8 迁移、API/Pydantic、状态、幂等、失败和回滚形成独立执行卡。
- 为 Provider 完整评测形成独立费用/请求/token 卡；合同批准不授权调用。

### P2 — 现有候选质量门

- 使用 `r1-claims-v1`、3 次哨兵、8 个保留案例各 3 次的既有完整门。
- 同时完成至少 20 个固定配置的真实慢路径性能样本；与质量样本是否重合必须在执行卡冻结。
- 保持真实模型、自动评分、人工语义复核和产品人验分栏。

### P3 — 正式定义交付

- v8 新增 Contract、审阅决定、发布回执和 Mission 完成回执。
- 新 API、Store、Agent terminal 校验、WorkBench 审阅/差异/导出完整实现。
- 先 fake/合成工程门，再用获准真实案例和精确构建完成人工验收。

### P4 — 批准知识复用

- v9 新增 ContextVersion、Suggestion、Decision 和投影状态。
- 第二个 Mission 必须实际读取一条明确选中的批准定义；撤销、过期、冲突和跨 Workspace 反例全部 fail closed。

### P5 — 可比较价值验证

- ContextOx 与 Codex/Claude Code 使用同一材料、目标、时间和预算。
- 记录事实/引用/未知覆盖、有效澄清、人工改写、主动操作、等待、总时长、失败和第二任务复用。
- 公开合成案例只证明可复现演示；真实价值保持 `NOT VERIFIED`，直到获准试点产生证据。

### B — 品牌与展示包

- 落地页、8 页动态 HTML、45 秒无声短片、8 页 PDF、A4 单页、Logo 包和分享卡使用同一故事与事实边界。
- GitHub Pages 工作流可以随候选进入分支；只有精确候选人工验收后才允许合并触发公开发布。

## 7. 验收分栏

每个切片都分别报告：implementation、static/typecheck、tests/build、runtime readback、real Provider、browser inspection、human acceptance、Pages publication 和 user value。自动检查不能写人验 PASS；分支 push、main merge 和 Pages deploy 不能互相替代。

## 8. 回滚与外部效果

- 数据迁移前停服、备份、检查无活动 Run/attempt，再单事务迁移并精确回读；不删除新历史来降级。
- 每个切片独立 commit；回滚用兼容修正或 revert，不 reset/clean。
- Provider 结果未知不自动重发；Pages 结果未知先读取 Actions/Pages 状态。
- 不增加 Provider、SDK、Agent 框架、MCP、向量库、通用工具、云同步或外部系统写入。

## 9. 材料决策复核

| 目标或约束 | 当前证据 | 反例／失败方式 | 合同中的处理 | 当前结论 |
| --- | --- | --- | --- | --- |
| 从候选定义走到正式交付 | Demo 已有候选、澄清、精确批准与导出，但仍是 `DefinitionDraft` | 模型自然停止、导出成功或 `agent_end` 被误写成业务完成 | Contract 发布与 Mission 完成使用独立版本、决定与回执 | 方向成立；P3 仍待精确批准 |
| 复用已批准知识且保持用户控制 | 现有连续对话可提供局部上下文，但没有跨 Mission 权威对象 | 历史内容过期、冲突、跨 Workspace 或被静默发送 | Context 版本再次批准；建议默认未选；Manifest 只收 accepted 精确版本 | 方向成立；P4 仍待精确批准 |
| 参考成熟 Agent 架构而不扩大工具面 | 当前薄 Python Loop、唯一 Provider 和串行领域工具已满足 V0 边界 | 框架迁移带来通用文件／Shell 工具、框架内存或错误完成语义 | 只借鉴 context transform、事件分层和追加式 session；领域状态仍由 ContextOx 管理 | 不采用框架迁移 |
| 用证据判断质量与价值 | 已有固定 rubric、Demo 和浏览器证据；正式 R1 与用户价值尚未证明 | 合成案例、自动评分或一次演示被宣传为生产价值 | P2、P5 分开；真实模型、人工语义、产品人验和用户价值分别记录 | 价值保持 `NOT VERIFIED` |
| 分享会物料可公开但不误导 | 品牌包使用公开合成画面，Pages 尚未触发 | 候选构建提前发布或把工程检查写成正式 Contract | 先分支候选与人验；只有精确候选通过后合并触发 Pages | 发布仍为 `NOT RUN` |

尚未解决且必须由人决定的门只有三项：受控文档精确 diff、P2 Provider 预算卡、品牌候选人工验收／Pages 发布。它们彼此独立，批准其中一项不授权另外两项。
