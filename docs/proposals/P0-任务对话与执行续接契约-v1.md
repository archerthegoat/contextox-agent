# P0：任务对话与执行续接契约提案 v1

日期：2026-09-06。contract_id：task-dialogue-v1。状态：PROPOSED；本文是精确评审对象，尚未作为已批准接口实施。

代码基线：main@1194329（产品代码与ec3142a一致）。本轮已按用户确认应用开发路径图精确修订，提交8b77368；其SHA256为6744d41bc18ae24cd9ba1c5e9df4604bceac6fd24bc83d65a26137f0de7c5831。旧实施计划中的“路线图待批准”保留为当时记录，以此处续记为准。

## 1. 本提案的范围与选择

实现任务内可回读消息、后续提问、合法结束与再次分析；复用mission_messages、runs、run_sources、context_manifests、既有七工具与单活动槽。保留partial和Mission未完成语义。纯解释仍通过finish_run受控结束，不将自然stop改为成功。

第一步可先交付§2只读接口及P2任务工作页，无需迁移。§3发送与续接需要§5的精确v4增量；在批准并实现前保持不可用。业务澄清回答/批准接口留给P5；waiting_for_human期间不通过泛用发送绕过裁决。

新增权限、Provider、依赖、队列、并发、预算数值、任意工具、正式Contract发布均不在此提案内。聊天按钮“发送”表示按明确资料范围发起一轮分析，不能被解释为零成本操作。

## 2. 公开类型和只读接口

沿用ID、Hash、UTC、Text、SourceIdentity、EvidenceRef和RunSnapshot。所有新Pydantic对象extra=forbid，整数/布尔严格；所有ID按Workspace与Mission父对象校验。源版本内容未授权不返回。

### 2.1 显式引用

```text
MessageReference =
 {kind:"source_excerpt", evidence_ref:EvidenceRef}
 | {kind:"source_column", source_ref:SourceIdentity, table_id:string<=4096, column_name:Key}
 | {kind:"draft_field", draft_id:ID, draft_version:PositiveInt, draft_sha256:Hash, field_key:Key}
 | {kind:"draft_relationship", draft_id:ID, draft_version:PositiveInt, draft_sha256:Hash, relationship_key:Key}
```

数组最多8项，不允许完全重复项，顺序保留。字段/关系引用必须属于当前任务的精确草案版本；来源引用必须属于当前任务及本次选中来源，存在且可读取；定位无效/身份未知关闭失败。查看历史版本允许，发送旧草案引用先拒绝为message_reference_stale，用户明确改为当前版本或引用旧来源证据后再发送，不自动重绑定。

### 2.2 消息读取

```text
TaskMessage = {
 workspace_id:ID, mission_id:ID, message_id:ID, created_at:UTC,
 role:"user"|"assistant", content:string(1..32768字符),
 original_attempt_id:ID?, run_id:ID?,
 references:list[MessageReference](<=8), sha256:Hash
}
MessageHistoryRef = {message_id:ID, sha256:Hash}
TaskMessagePage = {items:list[TaskMessage], next_before_message_id:ID?}
```

sha256=canonical({workspace_id,mission_id,message_id,role,content,references})；不含时间和sha256自身。用户旧原始输入已存库，按原文回读；旧assistant最终摘要按原文回读，references=[]，不根据旧流式文本倒推引用。新的user引用来自§5关联表；新assistant引用由同Run终止收据里的source_refs映射为source_excerpt，最多取前8个，完整证据仍以终止收据/草案为准；不声称展示的8个引用穷尽所有证据。

GET `/api/workspaces/{workspace_id}/missions/{mission_id}/messages?before_message_id=ID&limit=N`：limit默认20，范围1..50；before省略取最新页，结果按插入顺序从旧到新显示，next_before为本页最早消息ID（有更早项时），否则null。

使用当前表rowid作为内部插入排序，游标只传消息ID，每次在当前库重新解析rowid；不对外返回rowid，不依赖时钟排序。无消息返回items=[]/next=null；游标不属于当前任务返回404，不能回退首屏。分页按UTF-8序列化响应最多262144字节；从最新项向前装入，达到条数或字节上限即止，必保留准确下一页游标；单项放不下返回明确错误message_page_item_too_large，不能静默略过。

### 2.3 执行历史

```text
TaskRunSummary = {
 workspace_id:ID, mission_id:ID, run_id:ID,
 created_at:UTC, started_at:UTC?, finished_at:UTC?, status:RunStatus,
 last_sequence:Count, error_code:Key?, input_message_id:ID?,
 has_final_output:boolean
}
TaskRunPage = {items:list[TaskRunSummary], next_before_run_id:ID?}
```

GET `/api/workspaces/{workspace_id}/missions/{mission_id}/runs?before_run_id=ID&limit=N`：同上默认20/最大50、按插入顺序分页，查询必须读过严格Run校验，不能以摘要接口绕过旧receipt校验。旧Run input_message_id=null；不能猜测原始消息与每个Run一一对应。详情复用已有RunSnapshot与SSE，不新增日志全文接口。

只读接口可支持v3库；有v4关联表时补引用与输入消息关联。公开API不得向用户暗示尚未记录的历史答复存在。message_created事件仍只含ID/role，不把正文塞进SSE；UI收到状态变化后读取REST消息。

## 3. 发送、幂等与范围

```text
TaskMessageSendRequest = {
 kind:"message", client_request_id:ID, expected_state_version:PositiveInt,
 content:string(1..4096字符，至少一个非空白字符；不自动trim原文),
 references:list[MessageReference](<=8),
 history_messages:list[MessageHistoryRef](<=4，无重复ID，按原插入顺序),
 source_refs:list[SourceIdentity](<=8), provider_send_confirmed:true
}
TaskMessageSendReceipt = {input_message:TaskMessage, run:RunSnapshot}
```

POST `/api/workspaces/{workspace_id}/missions/{mission_id}/messages`：首次接受202，相同请求重放200，返回相同input_message和该Run当前快照。

GET `/api/workspaces/{workspace_id}/missions/{mission_id}/message-submissions/{client_request_id}`：已接受返回200同Receipt；确无记录404。404不是“先前请求绝未发出”的自动证明，前端仍需保留同一request_id核对/重提，不能生成新ID自动重发。

请求哈希=canonical_sha256(上述完整请求)，包含kind、原始正文、引用、历史选择、来源、expected_state_version和确认值；沿用runs.start_request_sha256。legacy RunStartRequest的哈希不变。相同client_request_id跨旧Run入口和新消息入口冲突，不混用两种请求。

发送步骤：

1. 先验证Workspace/parent与请求ID已有记录。已有同一消息请求且哈希相等则读回；不同哈希或旧入口占用返回409。已有结果的只读回执不执行模型；撤销的敏感内容不因重放绕过当前访问检查。
2. 获取现有runtime单活动槽。busy时不写入新消息/Run，不排队；先允许已有请求重放读回。
3. 同一写事务内校验expected_state、§4状态、当前授权/来源hash/引用、历史消息内容hash和上下文大小；任何失败全回滚。
4. 生成run_id与message_id，写Run、run_sources、user消息及run_message_inputs，并在允许时将Mission转active并增加state_version（原本active且首次开始时保持现有版本策略）；新Run的message输入只能一条。所有对象在事务提交前对读者不可见。
5. 提交后启动worker。线程启动失败则持久化agent_start_failed和原消息/Run，绝不创建第二条输入；客户端仍可按request_id核对。
6. worker领取queued后才发送模型请求；重复worker必须通过现有mark_run_running防重。发送期间断线只回读，不新开Run。最终答复通过§4收尾。

前端默认引用用户显式选择的字段/关系。历史默认建议上一组可用user+assistant消息，但发送前必须在界面显示携带条数并可查看/取消；实际history_messages以此次请求为准。用户主动发送下一条消息时生成新request_id，即使文字与之前相同也属于明确的新动作；同一次提交因网络失败核对/重提必须保持原ID与原负载，不能按文本相同与否替代动作身份。

## 4. 合法状态与公开答复

所有新发送先验证无活动Run、无未决ClarificationRequest、无in_review草案，防止状态标签不足以表达审批锁。旧接口原行为不偷偷扩大，但不得通过旧Start绕过新增的待决/越权检查。

| Mission及最近执行 | 新消息处理 |
| --- | --- |
| active、没有活动执行且无待决审批 | 接受 |
| blocked、latest partial且有效TerminalReceipt、无未决审批 | 接受；保留旧partial，新Run开始 |
| blocked、latest failed/blocked且无未知外部结果 | 接受显式新请求，仍做所有来源/权限检查 |
| blocked、latest cancelled且能确认取消前未发送或已知结果 | 接受显式新请求 |
| queued/running或runtime活动槽被占用 | 409/既有busy错误，不写入，不排队 |
| waiting_for_human或存在待批准草案/未回答问题 | 409 task_waiting_for_review；P5前不提供泛用继续 |
| Mission cancelled/completed | 409 state_conflict |
| 取消/超时/中断结果未知、usage_unknown或记录不足 | 409 previous_outcome_unresolved；保留回执，不提供自动重试 |

“已知结果”依据持久ProviderReceipt，不依据前端按钮或仅Run.error_code。无ProviderReceipt但曾有model_started也按未知处理；全部可见回执已终态且无outcome_unknown/usage_unknown/未知用量，并且没有无回执的模型轮次，才可认定本检查点可继续。响应已消费但usage缺失仍显示限制，暂不增加人工核销接口。

纯解释使用现有finish_run({outcome:"partial",reason:Text,source_refs})，reason作为本轮公开答复，最多4096字符，证据列表绑定终止收据。更新工具说明与P0_RUN指令，允许“本轮问题已回答，但任务整体未完成”的partial；不增加第八个工具、不增加新的Mission完成通道。

新消息Run在finish_run后用reason保存final_output和assistant消息，不再把整个Run的public_parts拼成最终答复。create_clarification/submit_for_review产生结构化卡；若未保存公开正文，显示“本轮已产生待回应事项”，该文本标明系统状态，不伪造assistant消息。自然stop没有合法TerminalReceipt仍terminal_result_missing。

旧Run保持既有公开摘要语义，不改写其消息。新Run在有效terminal后、保存公开正文前崩溃，仍保留结构化结果并显示“答复未保存”，不补造丢失文字；合法下一轮可引用其结构化结果。UI任务状态与本轮状态分开。

## 5. v4最小存储增量与兼容

不重建mission_messages，不复制整段对话或Provider transcript。v4只新增下表；旧表结构及其rowid顺序保留。

```sql
CREATE TABLE run_message_inputs (
    workspace_id TEXT NOT NULL,
    mission_id TEXT NOT NULL,
    run_id TEXT NOT NULL,
    message_id TEXT NOT NULL,
    expected_state_version INTEGER NOT NULL CHECK (expected_state_version > 0),
    references_json TEXT NOT NULL,
    history_messages_json TEXT NOT NULL,
    PRIMARY KEY (workspace_id, mission_id, run_id),
    UNIQUE (workspace_id, mission_id, message_id),
    FOREIGN KEY (workspace_id, mission_id, run_id)
        REFERENCES runs(workspace_id, mission_id, run_id),
    FOREIGN KEY (workspace_id, mission_id, message_id)
        REFERENCES mission_messages(workspace_id, mission_id, message_id)
);
```

正文只在mission_messages保存一次；来源在run_sources；client_request_id与request_sha在runs。新关联表保存输入消息及不能从旧行恢复的精确引用/历史选择/expected_state。三表组合能重建TaskMessageSendRequest并复核start_request_sha256；要求message为user、run_id一致、original_attempt_id=null，引用与history按Pydantic严格校验。

旧v3 Run无关联行，沿旧合同读取；新消息入口只有v4可写；v3部署该接口时返回明确的task_dialogue_not_implemented（503），不得假接收消息。旧Start在v4仍按旧请求形状保存，不强行伪造input_message_id。新用户输入与关联记录创建后不更新/删除；现有final_output幂等规则保留。

迁移仅在显式启动新版本服务且无活动任务时进行：确认精确v3结构、BEGIN IMMEDIATE、创建关联表、校验所有既有表/约束/foreign_key_check、设置user_version=4、提交。任一步异常回滚为原v3；未知schema拒绝。旧v1/v2先走既有事务迁移到v3，再执行v4；任一步失败不能宣称整体完成。只读doctor不得自行迁移。

备份必须在迁移前对停止的实例使用SQLite backup接口，连同来源目录及校验清单保存在原data_dir授权范围内的私有备份位置；不是简单复制活动WAL主文件。实际个人/客户库迁移的具体位置与保留方式在开工时核对，不用真实库做失败测试。

回退：旧应用拒绝v4是预期；未发生v4写入时可恢复经过核验的迁移前备份。已有v4输入后只允许保留v4数据的前向修复或兼容读取版本，不通过恢复旧备份丢失新消息，也不重建旧Run/回执。

## 6. 有限上下文与可追溯关系

本次消息与所选历史最多4条；将这些消息的正文、引用和hash序列化后最多65536 UTF-8字节。超出返回message_context_too_large（422），不截字、不丢引用、不静默省略历史。完整Provider请求仍受既有262144字节和其它RunBudget约束。

每条历史MessageRef先匹配持久TaskMessage.sha256。对应旧Run的来源范围必须是本次source_refs的子集；原始任务user消息只代表人输入，不自动授权附带源文件。任何历史/草案含未选来源证据，拒绝该历史选择或明确缩小草案片段后再发送；不能把未选来源正文混进摘要。当前任务的目标本身保持可见，不能以“聊天”扩展Mission范围。

数据链：ContextPacketManifest.run_id → runs.start_request_sha256 → 同Run的run_message_inputs + input_message + history消息hash + run_sources。每个模型回合生成manifest前，重建并验证这条链，构造同一MessageContext附到现有ContextPacket；worker不能以客户端自由文本替代持久绑定。关联记录及消息不可更新，所以旧manifest字段可沿用；本文将“显式manifest消息字段”和“通过不可变Run输入绑定”两种方案比较后推荐后者，以避免重建全部旧manifest。

ContextSnapshot增量（内部Pydantic，同源生成）：message_context可空；存在时为{input:TaskMessage,history:list[TaskMessage](<=4),request_sha256:Hash}。legacy Run为null。ContextPacket新增同名字段，仅包含通过上述范围校验的消息及受控引用内容。原ContextSnapshot验证必须覆盖嵌套Workspace/Mission、角色、哈希和来源。运行中不接受额外消息；每一轮由固定输入构建。

历史结果可以浏览，但本版发送草案引用要求最新版本；这是首版边界。消息正文是人的陈述或Agent候选，不因被放入上下文变成获批业务事实。

## 7. 错误、生成与历史Hash

新错误：task_dialogue_not_implemented（503）、message_reference_stale（409）、message_context_scope_mismatch（409）、message_context_too_large（422）、message_page_item_too_large（503）、task_waiting_for_review（409）、previous_outcome_unresolved（409）。其它沿用state_conflict、source/permission/version、store不可用等现有有界错误；不回显请求、文件内容、Provider正文或密钥。

更新finish_run说明/P0_RUN时生成新hash；保留确切已支持的旧(prompt_hash,tool_schema_hash)组合供旧Run回读，新Run写入必须匹配当前组合。不能独立放宽两个hash集合而接受从未存在的交叉组合。MessageContext绑定验证仅适用于有新关联行的Run；legacy字段读取保持原精确语义。

类型、OpenAPI、TypeScript与client由models.py及生成脚本产生；生成文件不得手改。现有SSE envelopes不增加消息正文。页面消息列表只从REST恢复。

## 8. P1诊断边界

本轮合成探针显示同一3000字节正文：单事件3272 wire bytes成功；3000事件324165 wire bytes在2427正文bytes后触发context_budget_exceeded且usage未知。证明累计SSE封装也消耗当前max_context_bytes，不能证明历史真实失败的唯一原因。

先增加内部可区分的固定阶段（request_body、http_headers、sse_wire、stream_content、agent_public_output、ipc_result），日志只允许阶段/已用字节/上限/轮次。内部ProviderError可携带固定阶段；外部错误code继续原值。本提案不改变传输、内容和IPC上限，不承诺增加日志能修复运行问题。后续若需分离传输预算或改变截流策略，必须以复现数据提出独立精确数值和失败边界，不能私自提高。

## 9. 实施与验收顺序

A. 只读查询/任务工作页：§2，v3库可运行，不调用Provider；保留资料预览，展示真实历史与明确空状态。
B. 合成诊断：§8，验证分片和各边界，不外发。
C. 发送闭环：§3–7，先在专用合成v3副本验证v4迁移、幂等和崩溃，再接右侧输入和至少两轮fake Provider交互；真实模型仍需具体调用授权。
D. 字段/关系联动：已有草案的多关系显示、引用与版本定位。
E. 澄清回答/正式批准：另行P5契约，不通过本提案解锁。

关键验证：页游标跨Workspace/不存在拒绝；多页无遗漏/重复；byte上限不跳项；v3/v4旧消息一致；重复请求只一条输入一Run；线程启动失败可按原ID核对；partial可继续；未知外部结果不重试；等待审批不绕过；旧请求API不能碰撞新消息请求；所选历史hash或来源变更拒绝；finish_run的reason成为受控答复，流式文本不覆盖它；terminal后崩溃不伪造答复；migration失败不改变原库，已有v4写入不回滚丢失；775px/宽窗口、刷新、任务切换与键盘可用。

## 10. 待批准的具体取舍

批准本文表示同意以下产品/数据合同，之后可按A–D实现及本地检查点提交；不包含真实模型调用、push、merge、部署或个人运行库迁移：

1. 任务内历史/引用随显式发送进入有限新Run；运行中无队列；等待业务裁决期间先禁用泛用发送。
2. 复用finish_run.reason作新消息Run的公开答复，保留partial；纯自然stop仍失败。
3. v4新增单张run_message_inputs表，旧消息正文、Run和manifest不重写；通过不可变Run输入关联证明消息上下文。
4. 首版范围/限额与失败行为按§2–7执行，取消/中断未知时先拒绝继续；更丰富的解释模式、历史引用、核销和澄清批准按后续真实需要扩展。

本提案与配套架构差异须在实施前获人明确批准；当前未修改架构报告或已批准共享契约正文。
